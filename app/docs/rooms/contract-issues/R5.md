## 1. What the API does now

* **Which rules a new draft gets** (DESIGN R-1.3). A settings document without the three keys means the old rules
  (`OLD_RULES`, the pydantic defaults R0 wrote), and the API writes them out at the next save. Every new draft gets
  `NEW_RULES`:
  * a draft with no recipe (a new project; a project with no saved recipe, the four seeded ones): revision 0 has them
    (`adopt.OPTIONS`, which now differs on purpose from the builder's), and `adopt()` writes them over the proposal's
    (the fake worker, and any worker of before the milestone, proposes none);
  * a draft from a saved version's recipe, or from another build's settings, **whose file names none of the three
    keys** (`adopt.carries_rules` on the raw JSON, before the defaults are filled in): `createBuild` writes them into
    revision 0 (`recipe_settings(..., new_rules=True)`), which the adoption keeps;
  * a recipe that names any of the keys is kept as it is, old, new or a legal mix (a missing one of them is the old
    rule, R-1.2).
  Switching a draft to the earlier way is one settings save with `OLD_RULES` (R6's button); saved versions never change.
* **`settings_issues`** (422 `invalid_settings`, `details.issues`; also `check_file settings`):
  * `slabs: 'closed-rooms'` with `ceilings: 'auto'` and / or `stairs: 'climb'`: one issue per offending key, at
    `/options/ceilings` and `/options/stairs`, each starting with the design's sentence "ceilings and climbable stairs
    need floor plates from the wall network";
  * `floors[].ceilingHeight`: 0.5 - 20 m or null (`/floors/<i>/ceilingHeight`);
  * the cap of 5,000 other fixes counts openings, outline edges, closings, rooms and stairs (`/fixes`);
  * a room fix's name: at most 200 characters, one line of plain text (N-3) (`/fixes/rooms/<i>/name`).
  `SetAside.floorPast` is a pydantic bool (a value that is not one answers FastAPI's 422; a missing one is false).
* **`adopt.rescale`** (R-6.3, U-7.4): a units change rescales the closing fixes' `a`, `b`, the room fixes' `at` and the
  stair fixes' `at` and `bottom` (null stays null) on the floors of that source, as the opening fixes.
* **`create_version`** writes `modelFormat: 'built-model/2'` when the model has the `stairways` key (an empty list too),
  else `'built-model/1'` (`builtmodel.model_format`, used by `seed.build.version_record`, so the seed and
  `create_version` share the one rule; every seeded model has no `stairways` and stays `/1`). The version's counts are
  unchanged: `rooms` counts `model.rooms` (the drawn names).
* **`checks.py`** (the Presentation checker the run-done validation and `create_version` use) accepts the v2 names of
  `contracts.ts`: the toggle `ceilings` in `labels` and `toggles`, and the part kinds `tread`, `landing`, `ceiling` in
  `partStyles` (N-5).
* **`check_file overlay`** checks the new floor fields and flag kinds through R0's pydantic models; no code change was
  needed (N-6). `builtmodel.validate` takes the v2 schema and rules R0 wrote; the twelve v2 broken cases are refused at
  the paths where the viewer throws (`test_r5_rules.py::test_the_v2_broken_cases_agree_with_the_viewer`).
* **The FakeJobRunner** (`tests/upkit.py`) answers a build run from `fixtures/rooms/runs/reference-build/` when asked
  (`FakeJobRunner(build_run=ROOMS_RUNS / 'reference-build')`): a v2 build passes the API's checks and saves as
  `built-model/2`.

## 3. How R5 read the design where it was silent or loose (information; accepted unless RI says otherwise)

* **N-1 Where R-1.3 decides.** The design names `adopt()` and "`drafts/builds.py:378` holds the raw file". The raw file
  is held at `createBuild` only, so that is where a recipe's rules are chosen (revision 0); the adoption keeps revision
  0's rules for a recipe build and writes `NEW_RULES` for a build with no recipe. Revision 0 shows the rules the draft
  will have (also to the worker's proposal, which starts from it). An open draft of before the milestone still at
  revision 0 (its first reading not done) keeps what its revision 0 has: the owner's store has none (R-1.3).
* **N-2 "Carries the keys"** = its raw `options` names at least one of `slabs`, `ceilings`, `stairs`. A recipe with one
  or two of them is kept, the missing ones being the old rule (R-1.2); a raw file that cannot be read (another build's
  `settings.json` gone between two reads) is kept as it is.
* **N-3 "A room name is at most 200 characters, text only"**: at most 200 characters and one line of plain text: no
  control characters (line breaks, tabs, C0 / C1). Null, empty and blank names are taken (no name; the builder reads
  them the same way). Markup is just text (the viewer and the web app use `textContent`).
* **N-4 The combinations** answer one issue per offending key, so the Floors step can point at the control.
* **N-5 The Presentation checker** (`checks.py`) is the API's own mirror of `contracts.ts` section 3, not one of R-12.1's
  three model checkers, so R0's change table missed it: without the new names a presentation that names the Ceilings
  label (R4.md: `presentation.labels.ceilings`) or styles a tread would fail every new-rule run's checks
  (`invalid_output`) and `create_version`. The seed's presentations do not change.
* **N-6 `check_file overlay`**: R0's pydantic models already type every new field (and refuse a null list, an unknown
  key, a stair state, a closing kind, a mouth that is not two points, a flag kind). R5 added tests, no semantic
  cross-checks (a flag's `ref.room` naming a space of the overlay, say): R3 writes the overlay at the same time, and a
  wrong reference would fail every build (`invalid_output`) for a problem the Check step can live with.
* **N-7 A fix's floor** is not checked against the floors (as for the opening fixes since the upload milestone): a fix
  on a floor that is not built is reported unmatched by the builder (R1.md section 5).
* **N-8 `modelFormat` lives in `seed.build.version_record`**, which `create_version` and the seed both use, through
  `builtmodel.model_format`; `store/base.py`'s `MODEL_FORMAT` stays the record's default.

## 5. What the other steps must know

* **R6.**
  * A new draft's settings (`getBuild`) already have `NEW_RULES`; a draft from a recipe of before the milestone has them
    at revision 0. "The earlier way" is one `putBuildSettings` with the three options at `OLD_RULES`; the button back
    puts `NEW_RULES`. `closed-rooms` with `auto` or `climb` answers 422 with issues at `/options/ceilings` and
    `/options/stairs`.
  * `ceilingHeight` 0.5 - 20 m or null; a room name up to 200 characters of one line (null or blank: no name); the 5,000
    cap counts the new fixes; `floorPast` must be a boolean.
  * The three counts of the Build and Save steps: from the overlay or the model (D-3).
  * A saved new-rule version's `version.json` says `built-model/2`; `VersionDetail` does not carry `modelFormat` (it
    never did).
* **R3.** The run-done checks accept `labels.ceilings`, `toggles.ceilings` and `partStyles.{tread,landing,ceiling}` in
  `presentation.json`; any other new presentation key is refused (`invalid_output`). The overlay's new fields are
  checked by R0's models only (N-6).
* **RI.** D-1 (`RUN_WITHOUT_THE_FLAG`), D-2 (`BANK_NEW_RULE_SHA1`), D-3, D-4. The real-worker tests took about 2.2
  minutes together on this machine (house 95 s with its conversion cached, bank 30 s from a cold cache, reference
  building 6 s). With `WT_INTEGRATION=1` they run against whatever builder is in the tree.
