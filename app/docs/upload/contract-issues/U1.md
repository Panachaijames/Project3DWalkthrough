# Contract issues: U1 intake and jobs (upload milestone, 4 Nov 2026)

Written only by step U1 (docs/upload/WORK_BREAKDOWN.md U1). The integration step UI settles each item. Items marked
**information** say how U1 read a silent or loose spot of the design; "accepted" then means the design is read that way
from now on. Items marked **for U5** / **for U3** ask another step to match what the worker does. U1 wrote no file
outside its own (`walkthrough_builder/{job, step, isolate, convert, losscheck, cache, runio}.py`,
`services/builder/tests/test_u1_*.py`, this file); `jsonfile.py` and `oslock.py` needed no change.

## 1. The venv's python.exe is a launcher: two processes, one identity (for U5; information)

`services/builder/.venv/Scripts/python.exe` is not the interpreter: it is a launcher that starts
`C:\Python314\python.exe` as its own child (checked: `Popen(...).pid` differs from the child's `os.getpid()`, and
killing the launcher kills the interpreter). So the pid U5's `LocalJobRunner.start` writes into `launch.json` is the
**launcher's**, while the worker's own `os.getpid()` is the interpreter's.

The worker therefore reports the launcher's pair in `job.json` (`runio.worker_identity()`: when this interpreter runs
under the venv launcher, i.e. its parent's image is `sys.executable` and `sys.executable` is not the base interpreter, it
takes the parent's pid and creation time; run by a plain interpreter it takes its own). `launch.json` and `job.json`
thus carry **the same pair**, as U-3.4 asks; both processes live and die together, so `alive()`, the start-up marking
and `taskkill /T /F /PID` (which takes the interpreter and its step children with it) all work on it. A worker test
asserts `job.json.pid == Popen(...).pid`. Each step child is the same: a launcher plus an interpreter, which is why
`isolate.py` allows 4 processes in a Python child's job (1 for leaf tools such as `dwg2dxf.exe`).

`runio.proc_start` follows U5's rule exactly (None for a process that has exited), and a U1 test compares
`runio.proc_start` with `walkthrough_api.jobs.local.proc_start` (run in the API's Python) and with Windows' own answer
(`Get-Process ... StartTime.ToFileTimeUtc()`) on a live child: all three equal.

## 2. ConversionReport.lostBlocks[].inserts: sheet metres need the units, known only after the read (information)

The contract says the lost inserts are in sheet metres, but the check step runs before the read decides the units
(U-7.4: the house says inches and is millimetres). The worker therefore keeps the cached `conversion.json`
(`<cache>/<sha1>/libredwg-0.14/`, units-free like the DXF beside it) with the positions in **drawing units**, and every
copy it hands out is in sheet metres: `out/sources/<sha1>/conversion.json` (prepare, after `read:i`, in the read's
`used` units; a one-source prepare after a units change publishes it again in the new units) and the build's
`SourceContext.conversion` (a copy under `out/tmp/`, in the settings' units). Conversion: `x / 1000 * openings.UNITS[u]`,
the reader's frame times the detector's scale, rounded to the millimetre. Nobody but the worker reads the cached file.

## 3. The audit (ezdxf.recover opens the DXF) runs beside the loss check (information)

U-6.2's success rule ends with "ezdxf.recover opens it". Opening a DXF with ezdxf costs as much as the read's own open
(bank L2 5.5 s; the suite about 45 s), so the worker runs it as its own step child (`step.py audit`, read's limits) in a
second Job Object **at the same time** as the loss check child (both only read the DXF), and merges its counts
(`dxf.acadVersion`, `insUnits`, `auditErrors`, `auditFixes`) into the report before committing the conversion to the
cache. A DXF it cannot open fails the run with `convert_failed` / `convert_timeout` / `convert_memory` naming step
`convert:<i>` (the `check:<i>` step that was running is marked failed too). `JobSpec.limits` has no entry for it; it uses
`read`'s. A DXF upload is not audited separately: its `not-converted` report takes the counts from the read's
`DrawingRead.dxf` (one ezdxf open, not two).

## 4. Blocks that came out SHORT are lost blocks too: the suite lists 15, not 11 or 12 (for UI; fixture)

U-0 counts "11 block definitions come out empty" in the suite; the contract says `lostBlocks` = "blocks whose definition
came out empty **or short**". The real check (by block handle, DWG side against DXF side) gives **15**: the 11 empty ones
of U-0 (the three `TG_artiscardio_2d_*` gym machines and `A$C59a32014`, which are placed inside the suite, and `kjhkjhh`,
`dgdgghjgg`, `22dab820-...`, `COT T7_HA`, `gdgdjgkhlljkj`, `COSCAODO`, `_DotSmall`, which are not placed in the plan at
all: `COT T7_HA` is inserted only inside `A$Cab429026`, a block nobody inserts) plus four anonymous dimension blocks
`*D1541` ... `*D1544` that came out short (9 items each). Totals as measured: 8,254 of 142,182 missing, 4,290 of them in
the plan (exactly the four placed blocks). The scaffold's provisional `fixtures/upload/conversion/presidential.conversion.json`
has 12 (the `*D` blocks merged by name) and upper-cased names; `fixtures/upload/conversion/bank1.conversion.json` has an
`other` message class and a note that the real report does not have (see 5). U1 does not own the fixtures: UI may
replace both with the real reports (`losscheck.check` on the reference DXFs, `publish(..., 'mm')`), which pass
`check_file conversion`.

## 5. Message classes: two more lines counted as `unhandled-class`; the `error:<kind>` rule (information)

`Warning: TODO TABLESTYLE r2010+ missing fields` (every Revit drawing here) and `Warning: AcDs ... segment yet unhandled`
(the house) are things the converter does not handle; counted as `other` they would add "the converter reported 1
message ..." to every bank and tower report. They are counted as `unhandled-class` (no note). `error:<kind>` keeps the
kind without numbers or positions: `buffer overflow` (any `... buffer overflow at ...`), `bit_read_*` (`bit_read_BL: ...`),
`Invalid <WORD[.field]>` (`Invalid ATTRIB.keep_duplicate_records`, `Invalid CMC`, `Invalid REGION.silhouettes`), else the
text up to its first digit or colon. The `error:*`, `unknown-object` and `other` classes add ONE note together ("The
converter reported 82 errors of 2 kinds; nothing is missing." for the house: its 81 ATTRIB lines and one buffer
overflow), and none when the verdict is `loss` (the loss notes say what matters). Verdicts measured: bank L1, L2, L29,
L30 `ok`; house `minor` (1 item on layer 0, 1 owner change); suite `loss`.

## 6. What `minor` covers (information)

`ok`: nothing missing, no type, layer or owner change. `loss`: an entity of model space, or of a block placed in model
space at any depth (through nested inserts), is missing. `minor`: everything else, i.e. nothing in the plan missing but
something changed (layers the decode did not know put on layer 0, empty layers on ATTRIB / ATTDEF, other layer, owner or
type changes) or items of blocks NOT placed in the plan (or of paper space) missing; the notes say which.
`renamedBlocks` compares names by handle with anonymous numbers and the layouts' numbers (`*Paper_Space` /
`*Paper_Space0`) dropped.

## 7. The worker runs the API's check_file in `validate` (information; for U5)

U-3.1's `validate` says "every output file passes `check_file` of its kind", and the builder never imports pydantic
(U-18.1). The worker runs the API's `walkthrough_api.check_file.issues()` on every JSON output in **one** child of the
API's own Python (`WALKTHROUGH_API_PYTHON`, default `app/services/api/.venv/Scripts/python.exe`, `PYTHONPATH =
services/api`), in a Job Object; it also checks itself that every output of U-3.1 is there, the model has floors and
parts, `report.json` is strict JSON, `topview.png` is a PNG and the `.ms` has CRLF lines and `(model data <stamp>)` on
line 2. When the API's Python is missing the record checks are skipped with a warning message (the API checks the
outputs again when it sees the run done). Measured: 1 - 3 s on the bank.

## 8. The prepare needs `paths.versionModel` too (for U5)

`propose_settings(..., latest_version)` needs `{model, msName}` of the latest version of a project with no
`project-data.json` (U-3.3; contracts.py). The worker takes them from `JobSpec.paths.versionModel` (the model.json path)
when the folder beside it has no `project-data.json`, and `msName` from that version's `version.json`
`downloads.maxScript`. JobSpec documents `versionModel` for the build's diff only: **U5 should fill it for prepare runs
too** (the four seeded projects' first upload needs it).

## 9. How U2, U3 and U4 talk to the worker (information; for U3 and U4)

* **Run errors with their own code:** a step raises any exception with a `code` attribute that is a RunErrorCode
  (`area_empty`, `align_failed`, `no_floors`, `bad_settings`, `detect_failed`, ...) and a plain-sentence message: the
  worker keeps both (`step.py` writes them to the step's result). Anything else is the step's `*_failed`; MemoryError
  exits 75 (`*_memory`). The error's `step` is the build step running when it failed (from `progress()`).
* **Progress:** `progress(name, f)` from U3 drives the build's JobRecord steps when `name` is `align`, `detect:<floor
  key>`, `walls`, `openings`, `furniture` or `outputs` (`step.py` reports `outputs` around `write_outputs`); other names
  are ignored. A step that gets a progress call becomes `running` (the one before it `done`); steps never reported are
  marked `done` with `seconds: null` when the child ends, or with `BuildResult.seconds[name]` when U3 gives one.
* **log()** lines become JobRecord messages (absolute Windows paths replaced by their last part) and go to `log.txt`.
* **The build child's environment:** `OPENINGS_DATA` is set to a fresh folder under the run's `out/tmp/build/` (the
  vendored `openings.py` / `prims.py` need it before they load), as well as `BuildContext.tmpDir` = `out/tmp/build`.
* **A DXF upload:** `SourceContext.conversion` and `dxfSha1` are `None` (no conversion), while the prepare still writes
  its `out/sources/<sha1>/conversion.json` (`not-converted`, `dxf.sha1` = the upload's sha1, audit counts from the read).

## 10. Small extensions inside U1's own files (information)

* `step.py` also runs `check` (the loss check) and `audit` (ezdxf.recover), besides WORK_BREAKDOWN's `read`, `suggest`
  and `build`, so that every parse of an untrusted file happens in a capped child, never in the worker.
* The test registry: `WALKTHROUGH_STEP_FAKES=<file>` makes a step child load that file first, which fills
  `step.REGISTRY` (`read`, `suggest`, `propose`, `build`, `outputs`, `check`, `audit`). Tests only. Run as
  `python -m walkthrough_builder.step`, the module is `__main__`, so `load_fakes` aliases it as
  `walkthrough_builder.step` first (otherwise the fakes would fill a second copy of the registry: found and fixed).
* Run errors for which RunErrorCode has no code: the check child's timeout or memory -> `check_failed` (there is no
  `check_timeout` / `check_memory`); the `suggest` child -> `internal`; a path over 260 characters -> `internal` with
  U-4.1's sentence ("The project folder is too deep for Windows: move it or shorten its path.").
* Worker exit codes: 0 done, 1 failed, 2 nothing to run (no run folder or no spec.json: no job.json written), 3
  cancelled, 4 interrupted (spec.json removed, or past `wallClockSeconds`), 5 the run folder was removed (nothing
  written). U5 reads job.json, not the exit code.
* The cache's `.done` lists each file's size and sha1 and is checked at every lookup (sha1 of a 105 MB DXF: ~0.2 s).
  Staging folders a killed worker left (`read-<rv>-tmp-*`, `libredwg-<v>.tmp-*`) are removed at the start of a run,
  with the eviction, while the machine lock is held.

## 12. Continuation of 9 Nov 2026 (information; for UI and U5)

The step was cut off on 4 Nov by the usage limit before it reported. On 9 Nov its files were read again from the
checkpoint (d946f56), every U1 test was run again, and three small changes were made in `job.py`, each with tests in the
new `tests/test_u1_job.py`:
* **The latest-version fallback** (`Run.latest_version`, handed to U2's `propose_settings`) now also requires that the
  project has no `project-settings.json`, as U-3.3 says and as U5's adoption (`drafts/adopt.project_frame`) and U2's
  `propose.py` read it. In every state the store can reach the answer is unchanged: U5 writes `project-settings.json`
  only at createProject (no version yet) and at save (whose version has `project-data.json`).
* **The LibreDWG folder:** `JobSpec.paths.libredwg`, else `WALKTHROUGH_LIBREDWG_DIR` (relative to `app/`, U-13.5), else
  `vendor/libredwg-0.14-win64`. U5 always fills the spec, so this only matters to a run started by hand.
* **`validate`** also checks what the build child says it wrote (`write_outputs`' `{name: path}`): each must be a file
  directly in `out/` (a missing or stray one is `invalid_output`).

**U5-7 is outdated (for UI):** U5.md section 1 says `launch.json` names the venv launcher and `job.json` the interpreter.
With `runio.worker_identity()` both carry the **same** pair: on 9 Nov a worker started through U5's own
`LocalJobRunner.start` wrote `job.json` with exactly `launch.json`'s pid and `procStart` (pid 29784, the launcher), both
`alive()` while it ran and neither after it ended; the worker test asserts `job.json.pid == Popen(...).pid`. The API's
behaviour is right either way (it judges by job.json's pair when there is one, and `taskkill /T` takes both
processes); only U5's note needs the correction.
