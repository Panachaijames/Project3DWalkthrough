## 2. The API's frozen part (U-13): how the scaffold wrote what the design leaves open

* **If-Match and Accept-Encoding are read from the request, not declared as parameters** (the foundation's precedent:
  `putFurnitureHeights` reads If-Match the same way). `putBuildSettings` and `getBuildPlan` take `request: Request`;
  OpenAPI and the generated client carry neither header. U-13.1's "+ If-Match" is honoured by U5's body.
* **Domain 422s** (`bad_project`, `bad_kind`, `bad_part`, `unsupported_version`, `bad_sources`, `invalid_settings`,
  `invalid_output`) are declared as `anyOf [ErrorResponse, HTTPValidationError]`, as `putFurnitureHeights` declares its
  `invalid_heights`: a malformed body still gets FastAPI's own 422. `test_error_responses_are_typed` checks 404, 409, 411,
  412, 413 and 503 are `ErrorResponse`; `test_upload_statuses` checks the domain 422s.
* **Empty bodies**: `RunBuildRequest`, `CancelBuildRequest` and `CompleteUploadRequest` (the last has no name in
  upload-contracts.ts: its body is `{}`) are models with `extra='forbid'`: `{}` only.
* **The part body** is `bytes` with `Body(media_type='application/octet-stream')`: OpenAPI 3.1 writes it as
  `{type: string, contentMediaType: application/octet-stream}`, and Hey API 0.99.0 generates `body: Blob | File`
  (checked). FastAPI reads the whole part into memory before the route runs: at most 8 MiB, the body guard's limit.
* **The body guard** (`bodyguard.py`, complete): a declared Content-Length over the limit is refused before the body is
  read; a chunked body is read up to the limit and refused the moment it passes it (else handed on unchanged). It sits
  inside CORS (its 411 / 413 carry the CORS headers). PATCH is guarded like POST / PUT.
* **BuildSettings' patterns** (floor keys, naming, office id) are in the field descriptions only, not pydantic patterns,
  so a bad value reaches `settings_issues()` and gets 422 `invalid_settings` with `details.issues` (U-13.2), not
  FastAPI's 422. `settings_check.settings_issues(settings, *, adopted=True) -> list[{path, message}]` is a stub returning
  `[]` (U5 completes it; `adopted=False` for revision-0 settings, whose units may be null).
* **Optional keys that are never null** (`Vocabulary`, `Flag.ref`) are pydantic TypedDicts (total=False, extra
  forbidden), so the generated client has `stairUp?: string` (not `| null`) and a present key is never written as null.
  The generated `BuildSettings`, `BuildDetail`, `UploadSession`, `SourceFile` and ten more section 5 types are mutually
  assignable with `contracts.ts`'s (`apps/web/test/upload-generated-types.test-d.ts`).
* **Raw files are checked by their JSON names only**: `check_file` validates with `by_alias=True, by_name=False`, so a
  worker writing `run_id` instead of `runId` is caught (the API's own request models still accept both, as
  `populate_by_name` does in models.py).
* **check_file kinds**: the 15 of WORK_BREAKDOWN plus `api` (RunApiRecord), `office` (OfficeMapping) and `inputs`
  (VersionInputs), which the worker and the API also write. VersionInputs and OfficeMapping are in `models_upload.py`
  (not in a route) because JobSpec carries an OfficeMapping.
* **`deps.get_jobs`** returns `app.state.jobs`, a `StubJobRunner` (`jobs/stub.py`) whose calls answer 501 until U5's
  LocalJobRunner; `jobs/base.py` holds the `JobRunner` protocol (start, cancel, alive).
* **Pinned counts** changed on purpose: `test_openapi.py` (24 more operation ids, 37 in all; the success response's
  description checked on 200 / 201 / 202 / 204), `test_routes.py` (37 routes over 7 modules) and also
  `test_smoke.py::test_openapi_operation_ids`, which WORK_BREAKDOWN does not list but pins the same ids.
* **A foundation quirk** (for U5): the API suite's `conftest.py` sets pytest's basetemp to `<WT_TMP>\api-tests\pytest`
  and pytest does not create its parent: with a fresh WT_TMP the suite errors at setup until `<WT_TMP>\api-tests` exists.
  CLAUDE.md says to `mkdir` it once; U5 may make conftest create it.

## 3. The builder's shared modules: how the scaffold read U-7.2 where it is silent

* **`keys.sig` follows `plan_items._signature` to the letter**, including its rule that EVERY `LINE` is read backwards
  (so two LINEs drawn in opposite directions have different signatures) while an open polyline is read from its lower
  end. Coordinates are rounded to 1 mm, `-0.0` counts as `0.0`, and the tuple is hashed as compact JSON (sha1, 12 hex).
  The INSERT branch keeps `name` and `path`, as the dedupe does.
* **`keys.rsig` of a nested INSERT** (an INSERT inside an element's block) uses the block's FAMILY instead of its name,
  drops the path, and takes its turn relative to the element's turn: a Revit re-export renumbers the element ids those
  names carry, and rsig must survive that (U-7.2). For every other item it is `sig`'s tuple with the points relative to
  the element INSERT.
* **`names.element_id(path)`** takes the item's block path; for an INSERT item the caller passes its path plus its own
  name, so an element's own INSERT carries its id (U-7.2 says "the innermost block name in the path").
  `names.element_depth()` gives the index of that name: the element INSERT's key is the first `depth + 1` components of
  the item's key.
* **Keys of MINSERT copies**: `virtual_entities()` of a MINSERT yields every array copy with the same `source_of_copy`
  handle, so U-7.2's key would repeat. The scaffold's provisional reader (`tools/upload/fixture_reader.py`) appends
  `~<index>` to a repeated part; U2 decides the rule (keys must be unique within a source, A-4).

## 4. Reading hostile drawings (for U1 and U2)

ezdxf 1.4.4 refuses names with `< > / \ " : ; ? * | = `` ` when it WRITES them, and READS them on line work, block names
and texts, but `recover.readfile` raises `DXFValueError` for the whole file when an **INSERT's own layer** carries one:
on load it adds a SEQEND to the INSERT and validates that layer name. AutoCAD never writes such a layer name, but a
hand-made DXF can. `tools/upload/make-test-dxf.py hostile` therefore puts `<img ...>` and `</script>` on line-work layers,
blocks and texts, and only `$'` and `&amp` (no `;`) on the INSERTs' layer. U2's reader should turn such a DXFValueError
into `read_failed` with a plain sentence ("a layer name the reader cannot take: ..."), and U1's tests may use a DXF with
one to check that path.

## 8. Builder tests do not turn warnings into errors

`services/api` runs pytest with `filterwarnings = error`; the builder's `pyproject.toml` does not: an error raised for a
numpy or shapely warning inside the vendored detector or the bank builder would be caught by their `except Exception`
blocks and change what they do, so a test would no longer run the code production runs. A test that wants a warning as
an error marks itself.
