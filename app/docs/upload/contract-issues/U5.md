# Contract issues: U5 API (upload milestone, 4 Nov 2026)

Written only by step U5 (docs/upload/WORK_BREAKDOWN.md U5). Nothing frozen was changed: `models.py`, `models_upload.py`,
the route decorators and `apps/web/openapi.json` are as the scaffold left them (`test_openapi.py`: the re-export is
byte-identical; `node tools/check-openapi-additive.mjs` passes). The integration step UI settles each item; "reading"
items say how U5 read a silent or loose spot of the design, and "accepted" there means the design is read that way from
now on.

## 1. Seams added inside U5's own files (no frozen shape moved)

* **`JobRunner.missing(kinds)`** (`jobs/base.py`): what the runner lacks to run sources of these kinds, as plain
  sentences; createBuild and runBuild answer 503 `builder_missing` with them (`details.missing`). The LocalJobRunner
  checks the builder Python (`WALKTHROUGH_BUILDER_PYTHON`), the builder package and, only when a source is a DWG,
  `dwg2dxf.exe` / `dwgread.exe` in `WALKTHROUGH_LIBREDWG_DIR` (a DXF-only build does not need LibreDWG). Cloud Run Jobs
  answer it their own way later.
* **`create_app(settings, jobs=None)`** (`main.py`): a test passes its own runner (`tests/upkit.py FakeJobRunner`);
  the served app uses the LocalJobRunner. The start-up work (U-3.4 marking, U-4.1 clean-up) runs in the app's lifespan,
  so `create_app()` alone (openapi_export, a TestClient used without `with`) touches no store.
* **`walkthrough_api.jobs.local.proc_start(pid)`**: the FILETIME rule for U1's comparison test (U1's `runio.proc_start`
  is the same code path: OpenProcess + WaitForSingleObject(0) + GetProcessTimes; a process that has exited has none).
* Store (`store/base.py` records, `store/drafts.py` methods): the five section-2 records as `Record`s; the methods of
  U-13.4, plus `check_path` / `deepest_run_path` (U-4.1), `build_lock`, `run_ids` / `run_dir` / `new_run_dir` /
  `remove_run`, `delete_build` (removes build.json under the lock) + `remove_build_dir` (after it: Windows cannot remove a
  folder holding the open lock file), `iter_builds`. `store/filelock.py` gained the generic `file_lock(path, timeout,
  busy)` behind the store lock and the per-build lock; its handle is opened `O_NOINHERIT`, so a worker started while the
  build lock is held never inherits it.

## 2. Readings of the design (information; accepted unless UI decides otherwise)

* **`JobSpec.paths.previousRun`** = the previous done-and-validated build run's FOLDER (`.../runs/0003-build`), and
  `versionModel` = the latest version's `model.json` (written for prepare runs too: U1's `latest_version()` reads it for
  U-3.3). U1's worker accepts a run folder, its `out/` or a model path for `previousRun`: compatible.
* **`JobSpec.office`** = the office memory of the settings' office (prepare runs only), null otherwise.
* **Revision-0 settings** (U-3.3): the project's names (meta.json), office and naming (project-settings.json; else, for
  a project with no settings, its latest version's photoName / maxPrefix / .ms name; else derived from the names),
  sources with `units: null`, no layers, no floors, U-10.4's defaults, offset pinned when the project has one.
* **Adoption of a recipe build** (`from` a version or a build): the recipe stays; files the recipe had keep their units,
  new files take the units their read used; floors are re-pointed by file name at createBuild; every layer the recipe
  does NOT name gets the proposal's role (`setdefault`). Without that, a new file's wall layer would silently stay
  `other` in a build that "starts reviewed". A pinned offset (project-settings.json) replaces a recipe's `'auto'`.
* **Adoption, seeded project** (no project-settings.json, no project-data.json): naming and offset from the latest
  version, floor keys and names in model order (zip with the proposal's floors; a clash gets `_2`), office null. The API
  does this even if U2's proposal already did: idempotent.
* **`from` default** (absent or `latest`): the latest version when it has project-data.json, else none; an explicit
  `version` without project-data.json is 404 `version_not_found` ("v2 has no build settings"); a `build` whose settings are
  still at revision 0 gives its files but no recipe.
* **The effective run status** (U-3.4) is also applied when a run is READ, not only at start-up: a queued or running run
  whose worker is gone shows `interrupted` at once and the next request holding the build's lock writes it into job.json.
  A run with no job.json whose `launch.json` pid is dead is interrupted at once (that process can never write it); the
  60 s rule applies only when there is no launch.json (the API died between Popen and writing it).
* **The cancel timer** kills a run that is still `queued` or `running` 15 s after the cancel (also when it moved from
  queued to running meanwhile), after checking the pid's creation time; it waits for the pid to exit (30 s), and only
  then writes `cancelled`. A worker that died without answering is written `cancelled` too (cancel was asked).
* **The worker's stdout / stderr go to DEVNULL**, not to a file in the run folder: an open handle there would stop
  Windows deleting the run, the build or a replaced e2e store (U-3.4's fresh seed). The worker's own `log.txt` carries
  every child's output and its own errors. Its working folder is `app/` (never inside the store).
* **Two pids per worker (information):** `services/builder/.venv/Scripts/python.exe` is the venv's launcher, which runs
  the real interpreter as its child. `launch.json` names the launcher (the process the API started), `job.json` the
  interpreter (the worker's own `os.getpid()`); the API judges a run by job.json's pair when it has one, else by
  launch.json's, and both live exactly as long as the worker; `taskkill /T` takes both.
* **Node's job object (information, U-3.4 "not promised"):** processes Node starts (npm run dev, Playwright's web
  servers) sit in libuv's kill-on-close Job Object, and so does a worker the API starts there: when that Node process
  ends, the worker ends with it and the next start-up shows the run `interrupted`. A uvicorn `--reload` restart does not
  end it. U5 does not ask for CREATE_BREAKAWAY_FROM_JOB (a parent job that refuses breakaway would make every start fail).
* **putBuildSettings 409 `run_in_progress`**: while any prepare runs (U-13.1), and also for a UNITS CHANGE while any run
  (a build too) is going; a plain settings save during a build run is taken (that result turns stale).
* **putBuildSettings keeps the build's files**: `settings.sources` must be the build's sha1s in upload order with their
  uploaded names and kinds (422 `invalid_settings`, path `/sources`): other files are a new build.
* **If-Match on settings** is optional, as on the heights (last write wins without it); a value that names no revision
  is 412.
* **`BuildSourceInfo.conversion.lostInModelSpace`** = the number of model-space inserts of the lost blocks
  (Σ `lostBlocks[].inserts`), the Files step's "how many of their inserts lie on the sheet".
* **`BuildResultInfo.seconds`** = job.json's step seconds by step name; `finishedAt` = job.json's.
* **Run clean-up** (U-4.1 "older than the two newest done build runs and the newest done prepare run"): per build, the two
  newest done build runs, the newest done prepare that read EACH source (a one-source prepare after a units change holds
  only its file) and the newest full prepare (the suggestions) stay, with the last run and anything in progress; finished
  runs older than those go. Failed runs after the last success stay (they are the recent story).
* **Upload sessions:** `received` is the part files on disk (two parts arrive at once); an expired session answers 404
  `upload_not_found` and is removed when touched; an empty file is refused at createUpload (422 `bad_kind`); a file
  whose first bytes disagree with its extension (a DXF named .dwg) is 422 `bad_kind` with "rename it"; a refused
  completion deletes the session (its parts are no good). A same-sha1 upload returns the stored source's record (its
  first name).
* **`createProject`:** a given id is taken as it is (`' new'` and `'new\n'` are refused, never trimmed); reserved and taken
  ids both answer 409 `project_exists` with `details.suggested` (the reserved ones are "taken by the seed"); an unknown
  `office` is 422 `bad_project`; `newOfficeName` whose slug exists already reuses that office. The deepest path a prepare
  writes is checked first (U-4.1): on a store deeper than app/data a 40-character id can be refused with 500
  `path_too_long` and the plain message.
* **saveBuild:** the build is marked saved right after `create_version` (then project-settings.json, then the office
  memory), so even a failure in the last two never lets a retry make a second version. A label that is not 1 - 200
  characters of text is 422 `bad_label` (an ErrorResponse; the declared 422 is `anyOf [ErrorResponse,
  HTTPValidationError]`). The office memory is written when asked and the settings name an office; an office id with
  no file yet (one picked as "New office..." on a seeded project) is created with its id as its name.

## 3. Gaps in the contracts (for UI)

* **`versions/<n>/source/flags.json` has no contract type.** U5 writes `{ "format": "build-flags/1", "flags": Flag[] }`
  (the overlay's flags at save). Add it to upload-contracts.ts section 2 or 4 if anything is to read it.
* **"Remember for the office" per furniture word** (U-8.4, U-12.3) has no field in `SaveBuildRequest` or
  `BuildSettings`: the office's `furnitureWords` is never written in this milestone. A later contract change could add
  `SaveBuildRequest.rememberWords: string[]` (or a per-word flag in the settings).
* **Error codes not in U-13.1's table:** 500 `path_too_long` (U-4.1's plain message, `details.length`), 422
  `bad_label` (saveBuild), and 503 `builder_missing` on putBuildSettings when a units change needs the builder and it is
  missing (the decorator declares no 503 for that route; it is rare: the builder vanished between two saves).
* **U0-4 settled here:** the API suite's conftest now makes `<WT_TMP>/api-tests` itself.
