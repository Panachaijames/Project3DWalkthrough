# Contract issues: U7 (upload milestone)

Written only by step U7 (docs/upload/WORK_BREAKDOWN.md U7: the plan canvas and the viewer's CSV guard). Each item: what
the documents or another step's files say, what U7 did inside its own files, and what the integration step (UI) should
settle. None needs a frozen file changed.

## U7-1 Delete has no callback in PlanCanvasProps (U6 to handle; UI to confirm)

U-12.1: "Keyboard: Esc clears, Delete = set aside the selection". The frozen `PlanCanvasProps` (apps/web/src/plan/index.ts,
U-15.1) has `onSelect` but no set-aside callback, so the canvas cannot set anything aside itself.
**Done:** the canvas handles Esc (`onSelect([], 'replace')` when something is selected) and leaves Delete alone: it does
not call `preventDefault` or stop the event, so the keydown bubbles from the focused canvas to the page (tested:
`apps/web/test/plan/canvas.test.tsx` "keys"). **U6:** the check step's wrapper listens for `keydown` Delete / Backspace and
sets the current selection aside (the same action as its Set aside button). Written in index.ts's notes.

## U7-2 The scaffold's placeholder assertions in `apps/web/test/upload-scaffold.test.tsx` (U6's file; no change needed)

That test (U6's after the scaffold) checks the placeholder: `[data-plan-canvas="placeholder"]` text `Plan of N items`,
`proposeAreas(bank1, {0}) == []`, `nearLayers(bank1, {0}, 1).size == 0`. With U7's bodies it still passes, for reasons
that are now real behaviour, not placeholders: where no 2D canvas context exists (happy-dom; a browser that refuses one)
`PlanCanvas` renders a text placeholder naming the plan (`... (this browser cannot draw the plan)`); layer 0 of bank1
holds only the view block's INSERT anchor (no drawn point), so the clustering finds nothing and no wall segment exists.
If U6 rewrites that test, the placeholder describes the fallback only. In a browser the canvas is
`[data-plan-canvas="canvas"]` with one `<canvas>`.

## U7-3 Block picks never select a view or xref block holding a quarter of the sheet (decision; UI to confirm)

U-12.1 "block": the innermost INSERT whose subtree holds the clicked item, climbing one level per click. A Revit view
block or an xref can hold most of a sheet, and a block-mode set-aside of it would remove a whole floor.
**Done:** anchors whose subtree holds 25 % or more of the sheet's drawn entries are left out of the chain (`decode.ts`
`bigAnchors`); a click whose only block is such an anchor selects the item itself. On the fixtures nothing is left out
(no block of bank1 or of the house sheet holds a quarter of its sheet), so every documented behaviour is unchanged;
the rule only guards against a drawing that is one big xref.

## U7-4 `DecodedPlan.extents` is the box of every point (kept from the scaffold); the view fits a robust box

The scaffold's `decodePlan` (real, "U7 keeps its signature and behaviour") sets `extents` to the min / max of every point.
On the house sheet that box is 413 x 417 m (stray items far out), while drawing.json's `extents` (the 1 - 99 % box) is
119 x 48 m. **Done:** `extents` unchanged; the canvas fits its view to every point unless that box is four times the
1 - 99 % box of the points, then to that box grown by 10 % (`decode.ts` `fitBox`). **U6:** for a sheet's size in text,
drawing.json's `extents` is the better number.

## U7-5 Flags and diff records of other floors (behaviour stated; U6 may pre-filter)

`Flag.at` and the diff's outlines are in "the flag's floor's sheet", while the canvas shows one source's sheet.
**Done:** with an `overlay`, the canvas draws the flags of `overlay.key` (and flags with `floor: null` that have a place)
and the diff records of `overlay.key` only; with no overlay, every record that has a place. Written in index.ts's notes.

## U7-6 A-6 "left of the panel" read as "clear of the panel" (UI to confirm)

ACCEPTANCE A-6: "at 1400 x 880 the start view shows every slab corner inside the canvas, left of the panel (U-11.2)". The
viewer's panel is on the LEFT (`[data-wt=panel]` at x 12 - 372 px on the seeded files), and the fitSlabs camera pans the
slabs right of it (`panForPanel`). **Done:** `tests/e2e/upload-walk.spec.ts` checks every slab corner (top and bottom of

`fitSlabs` camera (every uploaded version, U-11.2); for a fixed camera reported only: the seeded bank v2 has 11 of its
108 slab corners (L2's south-west) under the panel, the seeded hotel (fitSlabs) has all 284 clear.

## U7-7 What upload-walk.spec.ts needs from the integration run (UI)

* `WT_UPLOAD_OFFLINE_DIR`: a folder with only the uploaded versions' offline files (make-offline.mjs `--project` per
  project, or a copy of just those files): every `.html` in it is checked.
* `WT_UPLOAD_DATA_DIR` (**new**, read by the spec in its own process; the config passes only `WT_UPLOAD_OFFLINE_DIR`,
  and only to the API): the acceptance store, for the `.ms` line-2 check. Default `app/data`, right for the seeded bank.
* `WT_UPLOAD_WALK_SHOULD` (**new**): comma list of file names (without `.html`) or project ids whose walk checks are
  "must run, should pass" (the house, the suite, the tower): their failing probes are recorded and the tests pass; the
  loading and stamp checks still must. Without it every file must pass everything (the bank re-upload).
* Every probe goes to `<WT_TMP>/upload-walk/<file>.json` (per check: `ok`, `failures`, `detail`) for GAPS.md.
* Measured on the five seeded files (none marked "should"): bank v1, bank v2, the suite pass every check; the hotel
  passes every check (its start view judged: fitSlabs); the house fails the stamp check (the seeded house has no 3ds Max
  script; every uploaded version has one, U-11.5) and 11 of 32 doors with doorWalks (exterior doors not marked
  `exterior`, doors whose head stops you: the house's prototype test judged doors its own way, structure.spec.ts
  `walkThrough`). These are the kinds of gap A-6 expects on the house.
* PowerShell drops an empty variable: run with `WT_SERVE=none` there (the config starts no server for a value that names
  none); `WT_SERVE=` works in Git Bash.

## U7-8 The redraw budget is measured with a read-back after each frame (stated)

U-12.1 / A-10: "the house sheet redraws in under 50 ms in Edge at 1400 x 880". `tests/e2e/plan-canvas.spec.ts` times
`drawNow()` plus a one-pixel `getImageData` (the work actually done; the read-back moves Chromium's canvas to CPU
raster, so this is the slower path). Measured 4 Nov in headless Edge, two runs: whole house sheet (33,143 entries)
median 8.6 / 6.6 ms, the ground floor's area 18 / 16.5 ms, with the largest layer (21,495 items) highlighted 28.8 / 25.4
ms; at device pixel ratio 2 10.1 / 13 ms. The drawing's own lines are drawn 1 DEVICE pixel wide at any pixel ratio (Chromium's hairline path: 1.4 px lines
took 28 ms a frame on the same sheet); walls stand out by colour, not width (`colours.ts`).

## U7-9 The CSV guard (no issue)

`packages/viewer/src/furniture/logic.ts` `furnitureCsv`: the ten text columns pass the U-11.6 guard (a value starting with
`=`, `+`, `-`, `@`, TAB or CR gets a leading `'`, before the RFC 4180 quoting; a non-string value is guarded on its text;
null stays empty); the eight number columns never change. No field of the seeded models (nor of the foundation's furniture
test variants) starts that way, so the four goldens and the existing logic tests are unchanged
(`packages/viewer/test/unit/furniture/csv-guard.test.ts`). U5's `furniture_csv.py` should apply the same rule to
`str(value)` of the same ten columns, so the API's CSV and the viewer's stay byte-equal.
